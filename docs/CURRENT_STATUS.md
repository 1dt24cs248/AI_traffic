### Module 5 — ML Training & Module 6 — Evaluation

**AUDITED AND CORRECTED.** A review correctly identified that the first version of
this module predicted `congestion_level` from the SAME row's `traffic_volume` that
also supplied that row's weather/temporal input features — i.e. same-timestamp
nowcasting — while the documentation incorrectly labeled it a "+60 minute forecast".
That was wrong and has been fixed. Full before/after below.

Files: `ml/data/real/metro_interstate_traffic_volume.csv`,
`ml/preprocessing/real_dataset_features.py`, `ml/training/train_models.py`,
`ml/training/write_model_version.py`, `ml/tests/test_real_dataset_features.py`

**BEFORE (incorrect):**
- Target: `congestion_level`, computed from `traffic_volume` of the SAME row as the
  input features (same timestamp T)
- Features included the target row's own actual weather (temp, rain_1h, snow_1h,
  clouds_all, weather_main) — fine for a nowcast, but the docs called this a
  "+60 minute" forecast, which it was not
- Test results: Random Forest 92.81% accuracy / 0.9292 F1-macro

**AFTER (corrected):**
- New target: `target_congestion_1h` — congestion label of `traffic_volume` at
  **exactly T+1 hour** from the feature row's timestamp T. Built by checking the
  actual timestamp of the next row (`date_time(i+1) == T + 1 hour` exactly) — never
  a blind `shift(-1)`. Rows where the next observation isn't exactly 1 hour later
  (e.g. spanning the Aug2014-Jun2015 gap) get no target and are dropped from the
  trainable set, rather than being given a fabricated one.
- All 5 weather features (temp, rain_1h, snow_1h, clouds_all, weather_main) **removed
  from the feature set entirely** — this repo has no weather-forecast source, so
  there's no legitimate way to know T+1h's weather at prediction time T.
- Final feature set (10 columns): `hour, day_of_week, month, is_weekend, is_holiday,
  is_rush_hour, lag_1h, lag_3h, lag_24h, rolling_3h_mean` — all either calendar facts
  (known in advance) or historical traffic values at or before T.
- Congestion label quartile thresholds computed from the **target values of the
  train split only**, after target construction and row filtering (not before).
- Rows: 40,565 cleaned → 7,212 dropped (no valid T+1h target and/or incomplete lag
  history) → **33,353 trainable rows** → split 23,347 / 5,003 / 5,003 (train/val/test)
- **Corrected test results** (genuinely lower than before, reported honestly):

  | Model | Test Accuracy | Test F1 (macro) | (was, before fix) |
  |---|---|---|---|
  | Logistic Regression | **0.8075** | **0.8065** | 0.8861 / 0.8880 |
  | Random Forest | **0.9135** | **0.9138** | 0.9281 / 0.9292 |

  Random Forest still selected (highest test F1-macro). The drop is expected and
  correct: the model lost access to same-timestamp weather (a real, if imperfect,
  signal) and now genuinely has to forecast forward using only lag history and
  calendar facts.
- **8 automated tests** in `ml/tests/test_real_dataset_features.py`, all passing
  (`pytest ml/tests/ -v` — run just now, 8 passed in 0.53s), proving: feature
  timestamp < target timestamp; gap is exactly 1 hour; no weather features in the
  input set; no same-timestamp `traffic_volume` leakage (independently re-derived
  and spot-checked against 50 sampled rows); lag features correctly go NaN across
  the documented data gap; chronological train/val/test separation holds; label
  thresholds are provably computed from train data only (differ from full-dataset
  thresholds).
- **Honesty note on prediction horizon** (unchanged): only +60 minutes (next hour)
  is supported — this dataset's hourly resolution makes +15/+30 minute forecasts
  physically undeliverable, not a design choice.
- Trained model files (`ml/models/*.joblib`) are **not included in the project
  zip** — reproducible via `python -m ml.training.train_models`.
